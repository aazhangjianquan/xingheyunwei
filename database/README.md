# SQL 执行顺序

## v1.0.9 知识库空间开放范围

从 v1.0.8 升级时，先备份数据库、附件与实例密钥，暂停 API、Worker 和提醒调度器，执行本目录 `v1.0.9.sql`，再同步更新后端服务及前端。SQL 可重复执行；更早版本先按顺序升级至 v1.0.8。内置增量升级也补齐字段和新表，但多副本生产环境建议先执行 SQL。

原空间默认保持指定人员和原成员角色，个人库保持私有。全员或部门开放仅授予阅读权限，人员编辑权限仍单独维护。回退旧代码会收回部门/全员的隐式阅读权限，保留原直接成员；新增表和字段可保留。详见知识库权限变更记录。

## v1.0.8 项目岗位与审批执行

项目岗位独立于旧业务角色，支持从全部启用的平台成员中跨部门选人。销售/售前拆分并同时保留原成员，项目部门负责人改为技术负责人，移除项目管理者和产品开发。部门岗位、成员任职、多部门关系及基础角色保留；组织首审规则保持，运维审批和回填按关联项目的运维负责人、运维人员取人。

先备份数据库、附件与实例密钥，暂停 API、Worker、提醒调度器后执行本目录 `v1.0.8.sql`。从 v1.0.3 升级须依次执行 `v1.0.4.sql` → `v1.0.5.sql` → `v1.0.6.sql` → `v1.0.7.sql` → `v1.0.8.sql`。SQL 仅补充节点资格字段；首次新版 API 启动在事务中完成项目任命与旧授权迁移，验证后再启动其他副本、后台服务和新版前端。不能只升级镜像，不能向已有库导入安装或演示数据。

升级记录为 `system_settings.project_positions_v108`，旧任命与授权按同前缀归档；旧快照、审批历史与发布版本保持。旧全局流程若只明确指定一位运维负责人或回填人，会为缺少该项目岗位的项目补齐等价任命；多人时不猜测，管理员需在项目内指定。迁移不依据历史任务恢复已经撤销的项目成员。回退须同时恢复升级前数据库及旧镜像。详见 [变更与验收](../docs/project-position-routing-change.md)。

## v1.0.7 岗位授权与统一部门首审

备份数据库、附件及实例密钥，暂停 API、Worker、提醒调度器后执行本目录 `v1.0.7.sql`，再同步升级后端各服务和前端镜像。从 v1.0.3 升级依次执行 `v1.0.4.sql` → `v1.0.5.sql` → `v1.0.6.sql` → `v1.0.7.sql`。SQL 可重复执行，本次不能只升级镜像。

四类申请增加本次申请部门；旧记录不回填。首次启动将原直接业务授权迁移为等价部门岗位，保留项目关系和在途审批，新发布流程统一首审。成员角色仅保留基础与系统角色。选择部门只能来自本人已加入部门；负责人本人从上级开始，逐级负责人和其他启用管理员兜底，始终排除申请人。无人可审则提交前提示补齐配置。异常历史授权保留并记录在 `organization_business_positions_v107` 的 `unmapped_users`，修复组织后重启可再次迁移。完整回退需恢复备份，不能直接恢复旧镜像后丢弃岗位授权。详见 [变更记录](../docs/organization-position-approval-change.md)。

## v1.0.6 部门岗位向下引用升级

上级部门定义的岗位可被全部后代部门引用，上下级链路禁止新增同名岗位。人员岗位分配新增实际任职部门，同一成员可在多个部门分别引用同一岗位；现有岗位分配回填原定义部门，已有角色和项目关系保留。

升级前备份数据库与实例密钥，暂停 API、Worker 和提醒调度器的写入。远程当前为 v1.0.3 时，依次执行 `v1.0.4.sql`、`v1.0.5.sql`、`v1.0.6.sql`，再同步升级 API、Worker、提醒调度器和前端镜像。脚本可重复执行；本次涉及表结构变化，不能只升级镜像。历史同名岗位仅报告、不自动合并。启用继承分配后，不直接回退到不理解任职部门的旧代码。详情见 [岗位继承变更](../docs/organization-position-inheritance-change.md)。

## v1.0.5 个人提醒升级

先备份原库和密钥，暂停 API、Worker、提醒调度器，执行 `v1.0.5.sql` 后同步启动对应新版镜像及前端。新增 `personal_reminders`、`personal_reminder_recipients`、`personal_reminder_attachments` 三张表；不更改旧单据、角色或通知。SQL 可重复执行，API 启动也会创建缺少的表。当前远程版本为 v1.0.3 时先执行 `v1.0.4.sql`，再执行 `v1.0.5.sql`。附件沿用当前私有存储和备份，详情见 [个人提醒](../docs/personal-reminders-change.md)。

全新库：`mysql -u root -p < database/install.sql`。

已有首版库：先备份，再执行 `upgrade_v2.sql`，随后执行 `schema.sql`，最后重启 API。不要在已有业务库执行 `demo_data.sql`。

Docker 首次启动时自动依次导入 `schema.sql` 和 `demo_data.sql`。SQL 不包含飞书应用凭据或数据库凭据明文；演示账号初始密码统一为 `Demo@2026`，已用 PBKDF2 哈希保存。

## 组织、部门与岗位管理升级

远程版本为 v1.0.3 时，备份原数据库和密钥，使用新版 API 镜像运行 `python scripts/organization_precheck.py` 做只读预检查；名称冲突须先处理。暂停 API、Worker、提醒调度服务的写入后执行 `v1.0.4.sql`，再统一更新并启动新版后端和前端。API 启动也可自动补充表与字段；部门名称转为稳定 ID 的数据回填在 API 初始化时执行，仅执行 SQL 不会完成回填。

脚本可重复执行，不修改密码、直接角色、项目成员或审批快照。历史非空部门自动导入，空部门归属保留待分配；岗位和负责人不自动推断。管理员在「用户与权限 → 部门管理」补齐岗位并确认负责人。详情、预检查与回退方法见 [实施记录](../docs/organization-management-verification.md)。

## License 管理升级

已有 V3 数据库可执行 `upgrade_license.sql` 后重启新版 API；直接重启新版 API 也会自动创建新表。此脚本只创建 `license_requests`，可重复执行，不修改用户或旧单据。

管理员在「用户与权限」明确授予指定成员 `license_manager`（License 管理者）角色，普通申请者无需新增角色。新建库的 `schema.sql` 和 `install.sql` 已包含此表。

License 审批升级：已有 License 表执行 `upgrade_license_approval.sql` 后重启；直接重启新版 API 也会自动补字段。旧申请密文保留，待补走审批后才可读取。管理员在「系统配置 → 审批流程 → License 授权」指定最终审批人并发布，再提交历史申请审批。

License 关联项目：新版 API 启动自动增加 `project_id` 及索引、MySQL 外键，也可执行 `upgrade_license_project.sql`。新申请及驳回重提必须选择申请者有权限的启用项目；历史记录不按名称推断归属。历史待补审批申请需明确选择项目，在途及已完成审批保持原流程、状态和密钥。

## 审批流程与知识库升级

审批流程编辑器按 Jira Workflow 的状态机方式管理草稿、条件分支、会签/或签、处理人和发布版本；提交时冻结流程快照，详情页保留当前节点、意见、转交和历史轮次。

知识库按 Confluence 的空间、目录、文档状态和版本历史组织内容。新版 API 启动会创建默认「运维知识库」空间，把历史文章归入该空间并生成 v1 快照；也可手动执行 `upgrade_wiki.sql`。文档支持草稿、发布、归档，编辑会产生不可变版本记录。

## 操作日志升级

新版 API 启动自动增加业务操作日志字段及查询索引，也可执行 `upgrade_audit.sql`。旧日志完整保留在「接口访问与异常」，不会凭接口路径推断历史创建单号、修改前后内容或删除对象。

「业务操作」记录新版上线后的实际业务变动：操作人姓名及用户名快照、北京时间、业务类型、对象 ID / 单号 / 名称、具体动作和字段差异，过长文本会明确标记截断。业务日志与业务数据在同一个事务提交；失败尝试保留在接口日志。密码、License Key、飞书密钥和执行回填正文不进入字段差异。日志仅管理员可查询，没有修改或删除日志的接口。

## 请求限流与告警升级

新版 API 启动自动创建 `request_rate_limits`，也可手动执行 `upgrade_request_limits.sql`。表保存账号与 IP 的滚动窗口计数和告警去重时间，支持多进程共享；不更改原有业务、密钥、通知和审计记录。计数包含被限流的请求，健康检查、静态资源、CORS 预检除外。飞书收件人为当前启用的管理员，仍需启用通知并配置对应的 `open_id`。

## 私有化交付附件升级

新版 API 启动自动创建 `delivery_attachments`，也可执行 `upgrade_delivery_attachments.sql` 后重启；脚本可重复执行，不修改已有交付单。新库的 `schema.sql`、`install.sql` 已包含此表。

此表仅保存附件元数据。新附件原件及 PDF 预览缓存保存在 Compose 配置的 MinIO 私有桶，历史本地附件在迁移前仍使用 `api_instance` 卷的 `delivery-attachments/`。备份和恢复时必须配套保存数据库、整个实例卷与 MinIO 桶。更新 API 镜像后才具备 MinIO SDK 与 LibreOffice 文档预览运行时，仅执行 SQL 无法提供 Office 预览。

已有附件表的 MinIO 升级执行 `upgrade_attachment_minio.sql`，或由新版 API 启动自动补齐 `storage_backend`、`storage_bucket`；原记录默认保持 `local`，不推断历史文件已经位于 MinIO。运行 `docker compose exec -T api python scripts/migrate_attachments_to_minio.py`，逐个上传并回读校验大小与 SHA256 后才切换为 `minio`，保留本地原件，支持重复执行。新上传写入配置的私有桶，每条记录保留实际桶名。

## 变更附件升级

已有数据库执行 `upgrade_change_attachments.sql` 后重启 API；也可由新版 API 启动时自动创建 `change_attachments`。升级脚本可重复执行，不改动已有变更单。附件原件写入当前配置的私有 MinIO 桶，设置 `ATTACHMENT_STORAGE=local` 时使用私有本地目录；附件元数据保存于数据库。上传权限仅授予变更单创建人，查看、预览与下载沿用变更单可见权限。

## 飞书 open_id 加密升级

到期飞书提醒：新版 API 自动为资源和 License 增加提醒开关、修订号和修改人字段，并创建 `reminder_plans`、`reminder_deliveries`、`resource_reminder_contacts`。也可执行可重复运行的 `v1.0.3.sql`。历史单据默认开启；实际接入由独立调度服务按生效状态、有效期和最近适用节点进行，保留原有通知与密钥。更新时同步部署 API、Worker、前端和 `reminder-scheduler`，详情见 `../docs/expiry-reminders-design.md`。

`users.feishu_open_id` 使用应用主密钥自动加密写入数据库，应用 ORM 读取时才在内存中解密。接口只返回脱敏值，飞书通知发送前短暂解密，不把完整 open_id 返回给前端。新版 API 启动会迁移历史明文；也可先执行 `upgrade_feishu_open_id.sql` 扩展字段，再重启 API 完成迁移。必须备份数据库和 `api_instance/keys.json`，更换主密钥会使历史密文不可恢复。

## v1.0.1 角色与部门职责

已有业务库执行 `v1.0.1.sql`，同步更新 API、Worker、前端镜像。脚本仅合并旧角色到新角色；不包含演示数据，不清空业务、密码或审批历史，可重复执行。新版后端也能兼容未迁移的历史角色和流程快照。部门沿用 `users.department`，不增加结构或环境配置。职责和部署说明见 `../docs/roles-v1.0.1.md`。

## v1.0.2 知识库版本

`v1.0.2.sql` 为已有文章增加独立修订号 `revision`，可重复执行，API 启动也可自动补充。自动保存不再递增文档版本，手动保存成功才生成一个历史版本。已有版本保留；更新前后端后刷新编辑页面。详见 `../docs/wiki-versioning-v1.0.2.md`。
