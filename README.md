# 星河项目协作平台 · Vue + Python + MySQL

Vue 3 + FastAPI + MySQL 8，数据库名 `yunweishenji`。资源申请、变更管理、私有化交付、知识库、流程配置、审批任务、通知与审计均写入数据库。密码用 PBKDF2 哈希；交付密码和飞书密钥用 Fernet 加密。

Kubernetes 部署请看 [k8s-deploy/README.md](k8s-deploy/README.md)，纯结构安装文件为 [v1.0.0.sql](k8s-deploy/v1.0.0.sql)，关键配置变量与迁移对照见 [CONFIGURATION.md](k8s-deploy/CONFIGURATION.md)。K8s 包禁用演示初始化，使用统一 Secret 创建初始管理员；原 Compose 保留用于本机运行与迁移。

## Redis 与多副本架构（当前部署方式）

当前服务为前端 Nginx、两个 API 副本、Redis、通知 Worker、MySQL，附件继续存储在私有 MinIO。Redis 负责飞书令牌缓存和通知队列；请求限流及频率告警已停用；业务、权限、审计和通知发件记录由 MySQL 保存。完整架构、故障处理与扩容说明见 [Redis 架构文档](docs/redis-architecture.md)。

已有平台升级执行 `bash scripts/update_redis.sh`，脚本先构建，再停写备份并部署。全新部署运行 `docker compose up -d --build --wait`。当前 `docker-compose.yml` 已直接填写具体配置值，不依赖 `.env` 或主机环境变量；Redis 不向宿主机发布端口。复制到其他服务器、修改密码和目录用途见 [Compose 部署说明](docs/docker-compose-deploy.md)。

### 前后端独立服务

前端和后端分别由 `frontend/Dockerfile` 与 `backend/Dockerfile` 构建。前端使用 Nginx 提供 Vue 页面，后端只提供 API；修改前端无需重新构建 API。前端经 `/api/` 同源转发到后端，Nginx 动态解析 Docker DNS 并在运行中的 API 地址间分发请求。新副本或容器重建后约 5 秒内更新地址，接口连接失败会暂时避让；不可重复的 POST 不自动重放。

已有的合并服务升级请执行：

```sh
bash scripts/update_services.sh
python3 scripts/verify_services.py
```

脚本先构建两个镜像，再暂停 API 写入、备份 MySQL 和实例密钥，重建网络并启动前端与默认两个后端副本。沿用 `mysql_data`、`api_instance` 卷和私有 MinIO 桶，不清空数据。网络切换有短暂中断。备份在 `reports/services-backups/`，含密钥与业务内容，权限仅限当前用户；验收报告为 `reports/services-verification.json`。外部自定义数据库须先单独备份；脚本会停止自动操作。

全新部署与后续独立更新：

```sh
docker compose up -d --build --wait
# 仅更新前端
docker compose up -d --build --no-deps frontend
# 更新后端与使用同一镜像的通知 Worker（保留副本数）
docker compose up -d --build --no-deps api worker
# 临时扩至三个 API 副本
docker compose up -d --scale api=3 --wait
```

修改 `docker-compose.yml` 中 `api.deploy.replicas: 2` 为 `3` 可持久化副本数。API 不绑定宿主机端口、不设置固定容器名。浏览器地址仍为 <http://localhost:8080>，独立 API 入口为 <http://localhost:8008/docs>，前端 `healthz` 和后端 `/api/health` 分别供健康检查使用。当前不设置 IP、账号或平台总量请求配额，也不产生频率告警。审批、生成 License 与状态流转沿用 MySQL 事务及行锁；飞书通知提交 Redis Streams 队列，由独立 Worker 按数据库记录加锁发送，失败最多尝试 3 次，并跳过已经发送的消息。

所有副本共享同一 `api_instance` 卷（保留原有 `keys.json`，不生成新主密钥）、MySQL 与 MinIO。并发首次启动的密钥生成使用文件锁，数据库升级、种子初始化使用 MySQL 全局命名锁逐个执行。扩缩容不会重置账号、流程或密钥。不要运行 `docker compose down -v`。

单机 Compose 中全部 API 与 Worker 共享实例卷，不必再填写 `APP_SECRET` 和 `FERNET_KEY`。跨主机独立部署后端副本时，须从原 `keys.json` 安全复制两种主密钥，以相同的具体值填写到各主机的 `api.environment`，不能重新生成；同时连接同一数据库、Redis 与 MinIO，并共享实例目录或将历史本地附件先迁移至 MinIO。保存数据库连接配置后必须重启所有 API 副本。前端 Nginx 的 `API_UPSTREAM` 可指向后端负载均衡地址（`host:port`），`DNS_RESOLVER` 可设置部署网络的 DNS。独立域名直接访问 API 时，在 `CORS_ORIGINS` 填入允许的完整前端来源，用逗号分隔。前端镜像同源代理模式无需浏览器跨域配置。

Compose 内前端代理固定地址为 `172.29.90.10`，桥接网段为 `172.29.90.0/24`，后端只信任这个代理的转发来源；代理覆盖外部传入的转发头。自定义网络或增加入口代理时，须同步调整 `TRUSTED_PROXY_CIDRS` 为实际可信代理，不能信任任意来源。

工作台增加「License 申请」总数，进行中事项包括待审批与处理中 License，最近动态也包含 License。统计范围与 License 列表相同，过滤已删除及无权查看的记录，不查询或返回密钥。左侧统一显示「统一工作台」和 `PROJECT WORKSPACE`，登录提示使用项目协作文案。

后面的旧升级脚本和合并镜像说明保留作历史参考。当前版本部署请优先使用本节的独立服务命令；旧的仅构建 API 的流程不再更新前端。

## 升级已有 Docker 平台

部署交付附件功能：

```sh
bash scripts/update_profile.sh --attachments
```

脚本构建包含 MinIO SDK、LibreOffice 和中文字体的 API 镜像，停写后备份 MySQL 与完整实例目录，沿用现有数据卷更新 API。启动后把历史本地附件逐个上传至 MinIO，回读校验大小和 SHA256 后才切换存储记录，原本地文件保留；迁移可重复执行，失败会停止并显示实际原因，已迁移的记录不会重复处理。随后只读核对实际页面资源、附件接口、数据库表、MinIO 桶连接和文档预览运行时。备份在 `reports/profile-backups/`，日志和验收报告分别为 `reports/attachments-update.log`、`reports/attachments-verification.json`。首次构建需下载文档预览依赖，耗时会增加。此脚本的本地备份不包含远端 MinIO 对象，需另行备份对象桶。

部署个人资料与密码修改功能：在当前电脑的终端进入本项目目录，执行：

```sh
bash scripts/update_profile.sh
```

脚本先构建新版镜像，构建期间原平台继续运行；再短暂停止 API 写入，将 MySQL 和主密钥备份到 `reports/profile-backups/`，然后更新 API 并核对实际提供的 JS/CSS、右上角个人资料入口及姓名、密码接口结构。保留原数据库和主密钥卷，不创建验收账号、不修改真实账号密码。构建失败不会停止原平台；备份失败会尝试恢复原 API。更新后启动或验收失败会返回失败并保留备份及日志，不会自动恢复数据库。若平台改用了自定义数据库，脚本会在构建更新前停止，避免备份错误的数据库。

看到「部署完成」后打开 <http://localhost:8080>，按 `Command + Shift + R` 强制刷新，点击右上角头像进入「个人资料与安全」。部署日志为 `reports/profile-update.log`，验收报告为 `reports/profile-verification.json`。备份目录含数据库和主密钥，不要公开或上传。

完整 V3 流程升级与业务验收：

在项目目录执行：

```sh
bash scripts/upgrade_v3.sh
```

脚本暂停 API 写入，先备份 MySQL 和 API 密钥目录，再构建启动新版 API，最后在真实 MySQL 执行流程验收。原有 `mysql_data`、`api_instance` 卷保留，数据库自动做增量迁移。不要执行 `docker compose down -v`，也不要向旧库导入演示数据。

- 平台：<http://localhost:8080>
- API：<http://localhost:8008/docs>
- 升级日志：`reports/upgrade-v3.log`
- MySQL 验收结果：`reports/workflow-v3-mysql.json`
- 升级前备份：`reports/pre-v3-时间.sql`、`reports/pre-v3-keys-时间/`。密钥备份含敏感信息，不要公开。

验收会创建有 `V3验收` 标识的项目、用户与单据，临时发布测试流程后恢复原已发布内容与草稿（通过增加恢复版本，保持版本不可变）。测试通知只写数据库，不向飞书实际发送。建议在无人操作时执行。

全新安装可执行 `bash scripts/start_and_verify.sh`，或 `docker compose up --build -d`。Compose 仅运行 MySQL、Python API 两个容器；构建 API 镜像时先在 Node 构建阶段按锁文件安装依赖、编译当前 Vue 源码，再由 Python 提供生成的页面，服务器无需安装 Node。首次创建数据卷自动导入表结构与演示数据，已有卷不会重导入。

## 多角色与项目

管理员在「用户与权限」点击「管理角色」，可同时授予多个角色。成员统一使用平台账号密码登录。

新增岗位：项目负责人、项目经理、项目总监、销售/售前负责人、销售/售前总监、开发负责人。原有管理员、申请人、部门负责人、运维负责人、领导、运维人员保留；另提供独立的 License 管理者，共 13 种角色。角色目录由后端统一返回。

在「项目管理」创建项目、指定所属部门、项目负责人和项目经理，再为岗位选择成员。项目负责人和项目经理只能维护自己项目的岗位成员，不能创建项目、修改负责人/经理、授予全局角色或发布流程。成员必须先获得管理员授予的对应角色；申请人可作为项目的申请人岗位成员。

项目管理顶部显示项目总数、启用数和停用数。支持按项目名称、部门或成员关键词搜索，并组合所属部门、启用/停用状态筛选，显示匹配数量并可一键重置。统计和部门选项仅来自当前用户有权查看的项目；筛选不改变顶部总数，创建或保存项目后自动更新统计。

新建三类单据必须选择参与的启用项目。新增业务角色可查看自己的单据、参与项目的单据及分配给自己的审批；不会自动获得全局配置、全平台审计或凭据权限。原有运维负责人、领导和运维人员保留全局业务视图。凭据明文仅管理员、运维人员及对应交付申请人可查看。

系统管理员可为全部启用项目提交资源、变更、交付和 License 申请，无需另授予申请人角色或加入项目。管理员申请的审批归属部门使用关联项目的所属部门，部门岗位审批及部门条件均据此匹配；普通成员仍按申请人所属部门匹配。申请人身份和个人部门不变，代提交历史申请时以实际申请人的角色为准。审批归属部门随提交快照冻结，项目后续改部门不影响在途审批；驳回重提时重新匹配。项目部门缺少合格处理人时须先配置已启用且有对应角色的成员，管理员也不能审批自己的申请。

旧单据保留原文本项目名，`project_id` 为空，不推断项目归属。旧用户、飞书绑定、审批 ID、实际操作人和已通过进度保留。旧的在途工单将生成旧版流程快照，已通过节点不重跑。

## 私有化交付附件

创建私有化交付单时即可在「项目附件」选择或拖入多个文档，提交前可移除或重新选择。文件不符合类型、为空或超过大小限制时须先移除；申请提交失败保留已选文件，提交成功后在详情自动逐个上传到 MinIO。上传失败可单独重试，已成功的文件不会重复上传；详情仍可补充附件，关闭页面后未完成上传的本地文件需要重新选择。只有交付单创建人可以上传；预览、下载沿用交付单查看权限，后台逐次校验权限。支持 Word（DOC、DOCX）、Excel（XLS、XLSX）、PDF、TXT、CSV、Markdown、PPT、PPTX 和 RTF，单个附件不超过 20 MB，不支持空文件。

私有化交付已取消「数据库账号回填」和「账号权限验证」表单区块；新建、审批和交付完成均无需数据库账号。原新增凭据接口返回 410，历史密文记录、读取权限及审计数据保留。最后的执行节点填写交付说明并点击「完成交付」，无需提供数据库连接或密码。

Word、Excel、PPT、RTF 首次预览由 API 内的 LibreOffice 本地转换为 PDF，PDF 缓存同样写入 MinIO 私有桶，后续从桶读取；PDF 原件直接展示。转换和下载所需的本地临时文件处理后清理。文本支持 UTF-8、带 BOM 的 UTF-16 和 GB18030，以纯文本显示，超过 50 万字符时提示下载完整文件。文档转换失败会显示实际原因，仍可下载原件。转换分页及字体可能与 Office 原件有差异，公式和版式以原文件为准。

MinIO 的地址、AK、SK、桶名与区域均配置在 `docker-compose.yml` 的 `api.environment`：`ATTACHMENT_STORAGE=minio`，`MINIO_ENDPOINT` 为 `http://115.190.46.231:9000`，`MINIO_BUCKET=yunweishenji`，其余为 `MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY`、`MINIO_REGION`。修改后须重新创建 API 容器；仅执行 `docker compose restart api` 不会应用新的环境变量。HTTPS 地址自动启用证书校验，HTTP 地址按当前配置连接。API 不创建桶、不修改桶策略，使用已有私有桶；账号需要桶访问及对象 Get、Put、Delete 权限，Delete 用于失败回滚清理。

附件元数据保存在 `delivery_attachments`，每个附件记录自己的存储后端与桶名。新原件在 `delivery-attachments/originals/`，预览缓存在 `delivery-attachments/previews/`。浏览器始终通过平台登录接口获取文件，不接收 MinIO AK/SK、对象地址或预签名下载链接，桶无需开放匿名访问或浏览器 CORS。上传、预览、下载记录到对应交付单的业务操作日志。

新版 API 启动自动补齐存储字段；历史记录标记为本地存储，迁移前仍可读取。也可手动执行 `database/upgrade_attachment_minio.sql` 后重启；首次增加附件表使用 `database/upgrade_delivery_attachments.sql`。独立迁移命令：`docker compose exec -T api python scripts/migrate_attachments_to_minio.py`。连接失败、桶不存在或权限不足会明确报错，不会把新附件悄悄存回本地。备份和恢复须配套保存数据库、完整 `api_instance` 卷与 MinIO 桶；切换 endpoint 或迁移桶时须先同步对象，已有记录保留原桶名。

## License 管理

管理员先在「系统配置 → 审批流程」选择「License 授权」，配置审批节点，末节点可指定多位最终审批人，并选择全部同意、任意一人或任意 N 人同意，再发布流程。支持顺序审批、会签、或签、N 人阈值和条件分支，中间节点可按关联项目的岗位、申请部门岗位或固定成员匹配。申请者本人不能审批自己的申请；提交时没有合格审批人会阻止提交，不创建半张单据。

进入「License 管理」必须选择「项目管理」中的关联项目，再填写客户、产品、租户 ID、到期时间、账号数、Agent 数和用途。项目目录与资源申请相同，只能选择当前用户有岗位权限的启用项目（管理员可选全部启用项目）；后端根据项目 ID 写入项目名称，不能通过手填名称绕过校验。数量默认 `-1` 表示不限，到期时间按北京时间输入并转换成毫秒时间戳。提交后进入审批，个人待办也会出现在「我的审批」。驳回后只有申请者能修改重提，重新检查项目权限和启用状态，并采用最新发布的流程，旧轮次完整保留。在途审批不随项目或流程配置变动，停用或撤权的待办可由管理员转交。

最后一位审批人通过时，后端自动调用用户提供的 JAR，以 `-tenantId`、`-expireTime`、`-accountNumber`、`-agentNumber` 生成 License。完整 `{"license":{"body":"…","key":"…"}}` JSON 加密保存。Java 执行失败会回滚最后一次审批，修复环境后可重试；不会要求前面的审批人重复审核。

密钥仅申请者和实际完成最终审批的人可查看、复制。管理员、License 管理者和中间审批人没有默认密钥查看权；管理员转交末节点后，以实际审批人作为密钥查看人。列表、流程快照、审批历史和通知都不包含密钥。

管理员可在「用户与权限」给指定成员勾选「License 管理者」，允许查看全部申请与进度。其余成员只能查看自己的申请和被分配给自己的审批。该角色不授予系统配置权限。

JAR 位于 `backend/license-tool/`，Docker 镜像包含 Java。本地开发可设置 `JAVA_BIN`、`LICENSE_TOOL_JAR`。更新已有 Docker 平台：

```sh
docker compose up --build -d --wait api
docker compose exec -T api python scripts/verify_frontend.py
```

API 启动自动补齐审批字段并创建 License 流程草稿。已有未经过审批的申请（包括旧版已生成 Key 的申请）转为「待补充审批」，原密文保留并暂时禁止查看；管理员发布流程后，在申请详情点击「提交审批」，最终审批通过后开放给申请者和最终审批人。也可先执行 `database/upgrade_license_approval.sql` 再重启。升级后需要先配置并发布 License 流程，不能直接生成密钥。

项目关联升级在 API 启动时自动补齐 `license_requests.project_id`、索引及 MySQL 外键，也可手动执行 `database/upgrade_license_project.sql`。历史项目名称保留，不按名称猜测项目归属；历史在途和已完成审批继续原快照，密钥权限保持原规则。历史「待补充审批」申请须先选择申请者有权限的启用项目，管理员或 License 管理者代提交时也按申请者的项目权限校验。

## 成员角色与密码

新增成员采用「账号信息 → 分配角色 → 登录安全」三段表单。角色支持按职责分组、搜索、卡片多选和已选标签；成员列表点击「管理角色」，完成多项调整后统一保存。

新建成员和管理员重置密码均要求 **12–128 位**，且包含英文大写、英文小写、数字、特殊字符中的 **至少三类**。前端实时显示规则，后端强制校验；空格和中文不算特殊字符。已有账号的密码不自动更改，仍可使用原密码登录。

所有已启用账号均可点击右上角头像（也可点击左下角姓名），进入「个人资料与安全」，包括系统管理员、申请人、各类审批负责人、运维人员、项目岗位、License 管理者及多角色成员，无需额外授权。基本资料允许修改本人姓名（去除首尾空白，1–80 个字符），保存后同步账号展示；登录账号、部门、角色及飞书身份仍由管理员维护。登录密码通过当前密码验证后修改，需满足上述强密码规则，且不能与当前密码相同。当前会话保留，之后登录使用新密码。个人修改使用独立的 `/api/me` 与 `/api/me/password` 接口，仅作用于当前登录成员；姓名变更与修改本人密码均记录业务日志，密码仅记录已修改标记，不保存密码正文。

停用账号登录时明确提示「此账号已停用，请联系管理员启用后再登录」。已登录成员被停用后，下次访问接口会退出登录并保留停用原因。密码不正确、登录过期分别显示对应原因；修改登录账号或密码后清除上一次错误提示。

如果仍显示原生角色列表或「至少 8 位」，说明浏览器拿到了旧版页面。更新项目中的 `docker-compose.yml`、`backend/Dockerfile` 和前端源码后，在项目根目录执行上面的更新与核对命令，再刷新页面。Docker 构建现在直接编译源码，不依赖 `backend/public` 中的历史文件。核对脚本会读取运行中 API 提供的 HTML 和 JS/CSS，与镜像内文件逐项比对，不修改数据库。

## 审批流程配置

进入「系统配置 → 审批流程」，分别选择资源申请、变更管理、私有化交付或 License 授权：

1. 添加、删除、上移/下移审批节点或条件分支，填写节点名称。
2. 处理人可选固定成员、项目岗位或申请归属部门岗位；普通成员按申请人部门、系统管理员申请按关联项目部门匹配，自动去重并排除申请人。
3. 审批方式可选全部同意（会签）、任意一人同意（或签）或任意 N 人同意。固定成员支持多选；岗位会匹配全部合格成员，N 不能超过实际合格处理人数。
4. 条件分支从上到下首次匹配，要求最后有默认分支。条件可全部或任一满足，支持等于、属于、不属于。可用字段：环境、资源类型、变更类型、交付环境属性与审批归属部门。
5. 各分支结束后汇合到后续节点。末节点固定为运维执行/回填，可配置运维处理人。三类业务均必须回填执行结果才能完成。
6. 可保存未完成草稿；「校验」检查结构，「路径预览」选择申请人与项目计算路径、分支和处理人，不创建任务或通知。
7. 发布生成不可修改的新版本。编辑草稿不会改变已发布版本，在途单据不受后续发布或项目成员变动影响。

流程为无循环树：顺序节点可嵌套条件分支，分支最终汇合。最多 6 层、100 个节点。条件仅在提交和重提时计算，不支持在途流程迁移或预算条件。

提交时冻结流程版本、命中/跳过的分支和全部后续处理人。任何节点没有合格处理人会明确阻止提交，且不产生半张单据。停用账号、撤销岗位角色不会自动跳过任务，管理员必须在详情页逐个转交并填写原因。

每人通过自己的任务 ID 审批，管理员无默认代审批权；申请人不能审批自己的单据。会签未全部通过不流转；或签在一人通过后关闭其余任务；N 人阈值达到后关闭剩余任务。节点仍待处理时，任一有效驳回均退回申请人并关闭其他待办。只有申请人能修改重提，按最新已发布流程从第一节点创建新轮次，旧轮次与意见完整保留。详情展示流程路径、跳过分支、会签进度及转交历史。

审批、转交和重提使用事务及 MySQL 行锁；重复请求或迟到请求返回冲突，不重复流转。固定成员的提交时角色如被撤销也会阻止处理；岗位来源必须保留对应岗位角色。

## 飞书通知

License 到期前 1 个自然月、15 天、7 天、1 天，通过现有飞书机器人提醒申请人与实际完成最终审批的人；资源执行完成后，在结束日期前 7 天北京时间 09:00 提醒申请人与本单实际执行的运维人员。每张申请共用一个开关，默认开启，申请人及对应处理人可在详情修改，修改记录写入业务日志；关闭后停止所有收件人的后续到期提醒。创建申请时也可关闭，驳回重提保留原设置。

独立 `reminder-scheduler` 每分钟生成计划与通知，复用原 Redis 队列、Worker、飞书配置及重试入口。错过多个节点只补最近适用节点；发送前复核开关、有效期、周期和接收人，同周期已发送节点不会因重开而重复。资源历史执行人缺失时，管理员或运维负责人可在提醒区补录依据与人员。升级执行 `bash scripts/update_reminders.sh`，脚本先构建、备份数据库与主密钥，再更新 API、前端、Worker 与调度服务；也支持直接启动新版 API 自动补结构。备份在 `reports/reminder-backups/`，记录在 `reports/reminders-update.log`。

管理员在「系统配置 → 飞书通知」保存企业自建应用 App ID、App Secret、平台访问地址，并启用通知。App Secret 加密写入 MySQL，留空保留已有值。平台地址用于消息中的单据链接，需填写成员能访问的地址。

在飞书开放平台启用企业应用机器人、开通单聊消息权限（`im:message:send_as_bot`）并发布应用，将成员纳入应用可用范围。管理员在「用户与权限」点击成员的「配置 / 修改」，粘贴申请人、审批人或系统管理员的 `open_id`，保存后页面只显示脱敏值（例如 `ou_••••••••9abc`）。open_id 由数据库字段加密类型自动写入密文，通知发送前由 API 在内存中解密；列表、`/api/me`、审计详情和前端资源都不会返回完整值。检查应用凭据只验证鉴权，实际投递还取决于消息权限、成员身份和应用可用范围。

已有部署启动新版 API 时会把旧的明文 `users.feishu_open_id` 按持久化应用主密钥加密迁移，重复启动不会重复加密。数据库列已扩展到 500 个字符以容纳密文；也可下载并执行 `database/upgrade_feishu_open_id.sql` 后重启。不要手工把页面显示的脱敏值重新粘贴，修改时必须输入完整的 `ou_...`；清空输入可解除绑定。应用主密钥丢失会导致历史密文无法解密，必须和数据库一起备份 `api_instance/keys.json`。

通知覆盖资源申请、变更、私有化交付和 License 授权：

- 提交申请：通知申请人提交成功，列出当前环节与下一位处理人；同时给当前审批人发送待办。
- 审批流转：通知申请人进度与下一位处理人，给新进入节点的处理人发送待办。会签部分通过时仅更新申请人，剩余审批人不重复收到原待办。
- 流程完成：通知申请人登录平台查看结果。License 完成通知不包含 Key，交付通知不包含密码。
- 驳回与转交：驳回后通知申请人原因；管理员转交时通知新的处理人，并向申请人同步当前处理人。

平台统一使用账号密码登录，不再提供飞书登录、自助绑定或 OAuth 回调配置。升级会把历史登录开关改为「密码登录开启、飞书登录关闭」，保留账号、角色、已保存飞书凭据及通知 open_id；旧登录和票据接口返回停用提示。没有新的数据库字段，无需手动执行 SQL。

未启用通知或缺少收件人 open_id 时，通知记录标记为「待配置」，不阻止业务审批。投递失败可在「通知记录」重试；已停用账号不发送消息。真实飞书消息需要企业应用与收件人配置，验收测试使用模拟接口，不向飞书实际发送。

新增表为 `user_roles`（用户授权）、`projects`、`project_members`、`workflow_templates`（草稿及乐观锁修订）、`workflow_versions`（不可变版本）、`workflow_instances`（提交快照和轮次）、`workflow_nodes`（节点执行）、`task_transfers`（待办转交历史）。`approvals` 作为个人审批任务表增加 `node_run_id` 和处理人授权快照。`workflow_assignments` 仅保留兼容历史，旧写接口返回 410。

## 页面刷新与平台名称

平台名称以「系统配置 → 飞书与登录 → 平台名称」保存值为准。刷新首屏直接加载 MySQL 中的公共配置，重启不覆盖管理员名称。有效会话刷新后保留当前页面；网络故障显示重试，不清除令牌。只有真正的 401 会要求重新登录，重新登录后返回原路径。

刷新时静默恢复会话，不显示平台名称启动画面、加载文字或转圈；登录校验通过后显示当前页面。网络故障仍提供「重新连接」。

浏览器按域名隔离登录。Docker 页面在同端口的 `localhost` 与 `127.0.0.1` 之间，会统一到后台「平台访问地址」配置的本机入口，保留页面路径。API 与其他端口不会跳转。

部署此修复可执行 `bash scripts/update_refresh.sh`。脚本保留数据库、主密钥和后台名称，并验证升级前令牌在升级后仍可用，报告写到 `reports/refresh-verification.json`。前端回归：`node --test frontend/tests/*.test.mjs`。

刷新性能优化使用 `bash scripts/update_startup.sh` 部署。脚本先测量旧版，再构建 API 并复测，结果为 `reports/startup-profile-before.json`、`reports/startup-profile-after.json`。这些计时反映 HTTP 请求链，不包含浏览器执行、绘制及静态资源下载。业务数据只读，所有验收请求正常记录审计，不创建账号或单据。

生产首屏复用 HTML 中的数据库公共配置，只等待 `/api/me` 校验身份，页面数据随后在当前页面加载。项目页仅请求一次项目和角色目录，进入成员编辑时才读取用户目录；成员与角色批量查询。审计提交在线程中执行并等待落库，不占用异步事件循环；API 的 `Server-Timing` 区分接口处理与审计耗时。页面使用系统字体。隔离查询计数报告在 `reports/startup-query-before.json`、`reports/startup-query-after.json`。

## 审批流程与知识库

审批流程采用版本化状态机：管理员在「系统配置 → 审批流程」编辑草稿，按条件分支、审批节点、会签/或签/N 人阈值和执行/License 结束节点预览路径，校验后发布新版本。提交时会冻结流程和处理人快照；在途单据不受后续编辑影响。详情页展示当前节点、处理人、意见、转交历史和历史轮次，待办任务按当前账号权限返回。该设计对应 Jira Workflow 的状态、条件、处理人和版本发布边界。

知识库分为「个人知识库」和「公共知识库」，默认进入个人库。每位成员自动获得一个仅本人可见的个人空间，管理员也不能通过知识库、历史版本或操作日志查看其他成员的私人内容。所有启用成员均可创建公共库，创建人自动成为负责人。公共库采用邀请制，不代表对所有成员公开。

负责人在「空间设置 → 成员管理」搜索并添加启用成员，默认授予只读权限，可调整为编辑权限或移除。只读成员可查看全部文档状态及版本；编辑成员还可创建文档和编辑本人文档；负责人可维护库内全部文档。移除成员后，即使其为文档原作者，后续请求也不能继续访问。负责人只能转让给已加入且启用的成员，原负责人保留编辑权限；个人库不能添加成员或转让。

文档创建默认选择当前空间；编辑时不能更换所属空间。列表、正文、历史版本、搜索、统计与审计记录在后端统一校验空间权限。正文不进入新增审计日志。历史审计内容保持原样，但列表、搜索和详情会过滤无权访问的知识库记录。

启动新版 API 自动迁移，也可执行 `database/upgrade_wiki.sql`。已有空间保留为受限公共库，负责人保留管理权，原文章作者一次性加入为编辑成员；文章和版本不移动、不改写。成员初始化标记保证重启不会恢复已撤销的权限。安装及升级 SQL 与应用数据结构一致。

## 操作日志

管理员在「操作日志」默认查看业务操作，支持按单号 / 项目 / 关键词、操作人、业务类型、动作和日期筛选及分页。详情保留操作人姓名与用户名快照、对象 ID / 单号 / 名称、修改前后内容和来源 IP；时间统一为北京时间，过长文本会明确标记截断。创建、驳回重提、审批、最终生成 License、转交、回填凭据、项目及成员调整、成员启停、文章和配置变动均生成对应业务记录。未改动内容的保存不标记为修改。

业务记录随业务事务一起提交；失败与越权尝试在「接口访问与异常」查询。此标签也保留全部旧接口日志，不补造历史业务信息。密码、License Key、飞书密钥和执行回填正文不写入变更详情。管理员也不能从日志读取密钥。日志没有修改 / 删除接口。启动新版 API 自动迁移，也可执行 `database/upgrade_audit.sql`，不会删除已有日志。

## 请求与来源 IP 日志

当前已移除请求入口的限流检查，不再执行 10 秒/20 次、60 秒/120 次规则，也不设置账号或平台请求总量配额。连续访问正常进入认证、权限校验及业务处理，不再产生请求过频的 429、限流 Redis 故障的 503 或新的频率飞书告警。Redis 继续提供业务通知队列和飞书令牌缓存。

操作日志继续记录请求结果、操作人和来源 IP。已有计数表、历史安全提醒及相关结构保留，不删除历史数据；兼容的旧计数工具不参与 API 请求处理。

使用 Nginx 等反向代理时，在 Compose 直接填写 `TRUSTED_PROXY_CIDRS` 为实际代理的 IP / CIDR，多个用逗号分隔；只信任这些代理传入的来源地址，保证日志准确。当前固定为前端 `172.29.90.10/32`，换服务器整套部署时通常无需修改。
