## 实现

现有链路为业务生成通知文本 → `notification_logs` → 后台任务或 Redis 队列 → `feishu.deliver_notification()`。

`backend/app/notification_cards.py` 集中生成飞书 JSON 2.0 卡片；`backend/app/feishu.py` 在原投递入口选择 `interactive` 或 `text`，将内容序列化到 `content`。不新增数据库字段或迁移。

| 通知 | 展示 | 详情按钮 |
| --- | --- | --- |
| 四类申请的待审批 | 蓝色标题、项目与单号、申请人、申请类型、待处理环节 | 查看申请并审批 |
| 资源、变更或交付的执行待办 | 蓝色“待执行”标题、原任务信息 | 查看任务并处理 |
| License 四个到期节点 | 橙色标题、发送时剩余时间、客户、产品、北京时间、节点或补提醒说明 | 查看 License 详情 |

分栏在窄屏下上下堆叠，字段不设置截断行数。使用飞书普通文本组件显示业务字段，避免把项目名、客户名中的 Markdown、链接或 `@` 语法当作富文本。主题使用飞书标题主题与支持明暗模式的倒计时颜色。

审批卡片完整匹配持久化通知的已知字段布局，展示审批通知产生时的信息，而不是读取可能已经流转到下一环节的当前业务状态。旧消息、多行字段或不匹配的类型保留原文，避免丢失信息。卡片按钮按当前配置的平台地址与记录 ID 生成，沿用平台已有详情路由。

License 提醒在已有的发送前有效性检查通过后，用同一投递时刻更新审计原文和卡片。倒计时不是定时节点的固定“7 天”文案，延迟投递或重试时会重新计算。卡片只读取项目、单号、客户、产品和计划时间，不读取 License Key。

## 故障与回滚

- 飞书拒绝卡片时按现有状态记为失败，最多三次投递，保留原稳定 UUID；不另补一条文本消息，避免重复通知。
- 通知记录保留通用中文排障说明，卡片失败增加格式及客户端版本提示，只附加可校验的数字错误码，不记录服务端原始错误正文。
- 旧消息的文本回退是发送前的格式选择，不是一次失败后的第二次发送。
- 回滚只需移除 `feishu.py` 对卡片生成模块的调用、恢复 `msg_type=text` 与原文本内容；无需清理数据库。

## 生效方式

开发进程重新加载后端代码即可。已有 Docker Compose 部署需更新 API 和通知 Worker：

```sh
docker compose up -d --build --no-deps api worker
```

独立 Kubernetes 部署应使用新后端镜像，滚动更新 API 和通知 Worker。调度、前端和数据库结构无需因本次卡片改版升级。

卡片 JSON 2.0 需要飞书客户端 7.20 及以上；更早版本只能显示标题和升级提示。客户端内的最终排版以飞书原生卡片组件为准。
