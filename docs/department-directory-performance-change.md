# 部门目录接口性能优化

日期：2026-11-09。用户看到 Network 中 `GET /api/departments` 用时 4.47 秒，授权按批量查询优化并部署。

## 现状与改动

原接口在部门列表组装中逐部门读取成员、岗位和待办；每个岗位又分别查询成员、待办、项目数。待办按部门检查历史快照时，重复查询部门别名，产生大量 N+1 SQL。生产环境 16 个部门、5 个岗位只读剖析记录到 791 条 SQL；640 条是同一别名表查询。部署前暖 HTTP 的截图记录为 4.47 秒。

现增加一次性部门目录汇总，批量读取部门层级、成员关系、负责人、岗位与岗位权限、待办和项目成员数。一次性将部门名称及别名映射载入内存，用于解析在途审批的历史部门快照。现有响应字段、人数去重、部门负责人资格、岗位委派判断、项目关系和审批统计均保留；没有表结构或响应格式变更。

## 验证

独立回归加入 40 条待审批任务、8 个部门及两个分配岗位，验证待办、成员数、项目数正确且部门目录 SQL 小于 80 条。相关后端测试 65 项通过，前端 133 项通过，部署后两个 API 副本、17 项只读浏览器检查、服务负载均衡与 7 个服务健康检查全部通过。

生产数据剖析从 791 条 SQL 降至 11 条（减少 98.6%）；SQL 执行约从 555 ms 降至 55.5 ms。目录汇总组装耗时约从 946 ms 降至 83.7 ms。部署后连续 6 次预热 HTTP 请求为 49.0, 43.2, 47.8, 57.2, 57.6, 55.3 ms，中位数 52.15 ms。部署前后完整响应 SHA-256 相同：`2d3ec26d415f695116cc32bb6b463a4d70945ed7984f29eff7cb2d637dfc36bd`；16 个部门、5 个岗位及各部门人数和待审批统计完全一致。
