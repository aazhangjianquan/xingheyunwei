# 部门岗位向下引用变更方案

日期：2026-11-09。状态：用户已批准，岗位继承与个人提醒已一并部署，验收通过。

## 需求与验收标准

目标：岗位在上级部门定义后，全部后代部门可查看并为本部门成员分配，无须重复建岗；同一上下级链路禁止新增同名岗位。

以「产研中心 → 研发中心 → 灵搭业务部 → 后端组」为例，在产研中心建立「后端开发」后，三个下级部门都能看到并引用，页面注明「来自产研中心」。引用表示在所选下级部门任职，不会自动加入岗位来源部门。

1. 本部门岗位及任意层级祖先岗位都出现在岗位列表，以及新建成员、添加已有成员、调整组织岗位的选择框中；停用岗位可见、不可新增分配。
2. 子部门创建或重命名岗位时，与任意祖先已有岗位同名即拒绝，提示来源部门并引导引用。祖先创建或改名若与后代岗位冲突，也拒绝并列出冲突部门；平级部门可保留各自独立的同名岗位。停用岗位仍保留名称。
3. 同一成员可以在多个部门分别引用同一上级岗位。修改、移出某个部门只影响该部门对应的岗位分配，保留其他部门岗位、直接角色、负责人任命和项目关系。
4. 引用岗位定义由系统管理员在来源部门维护；下级列表显示来源提示和入口，岗位名称及权限模板共用一份定义，不产生可独立编辑的副本。修改模板或停用时显示所有引用部门的影响人数。
5. 部门负责人仅可在本人被任命的部门，为可管理成员分配允许委派的岗位。上级岗位的可见和引用不扩大人员管理范围，也不产生负责人任命。管理员仍可管理全部部门。
6. 现有同名岗位与人员分配原样保留，明确显示来源，不自动合并或改变角色；升级检查报告冲突，供管理员显式整理。后续操作不得新增上下级重名冲突。

保留现有多部门归属、子树人数去重、角色来源并集、负责人边界、项目关系和工单审批规则。不新增主部门或默认审批部门设置。用户已明确授权一并部署到当前平台。

## 从代码确认的当前行为

- `backend/app/models.py`：`DepartmentPosition.department_id` 记录定义部门；`DepartmentUserPosition` 只有成员和岗位两个主键字段，没有实际任职部门。
- `backend/app/organization.py`：目录只查本部门岗位；分配校验要求岗位定义部门与成员目标部门完全一致。替换、移出、岗位权限来源及统计都用岗位定义部门推断任职部门。
- `backend/app/roles.py`：按岗位定义部门检查成员归属，计算有效岗位角色；`organization.role_filter` 提供对应 SQL 筛选。
- `backend/app/main.py`：新建账号与管理员编辑账号也调用组织分配逻辑，默认岗位列表同样按岗位定义部门筛选。
- `frontend/src/OrganizationManagement.vue`、`MemberOrganization.vue`、`App.vue`：部门返回的岗位列表同时驱动岗位管理和三处人员分配入口，目前没有来源标记。
- 部门目录已使用批量汇总降低 SQL 数量，本次必须沿用批量层级、岗位、分配关系查询，不能逐部门逐岗位查询祖先和人员。

## 数据与交互设计

人员岗位分配增加 `department_id` 表示实际任职部门，唯一键调整为「成员、任职部门、岗位」。岗位本身的 `department_id` 继续表示定义来源。原有分配的任职部门回填为岗位定义部门；不改原成员部门关系及角色模板。

返回岗位数据时明确区分来源部门与当前使用部门；成员岗位输出继续用实际任职部门供界面筛选，并补充来源部门字段。岗位列表标注「本部门」或「来自 XX」，岗位选择框同步显示来源。引用本身不创建新岗位定义，也不添加来源部门成员关系。

权限与成员筛选统一改为按实际任职部门检查归属和启用状态，同时检查来源岗位及来源部门启用状态。部门负责人可否分配按当前使用部门判断，再沿用原有可委派权限模板限制。角色仍取独立有效来源的并集。

下级岗位卡片的人数统计按该部门及全部后代部门的实际分配成员去重；来源部门的岗位维护影响统计覆盖全部引用部门，按成员去重。删除岗位仍要求先解除所有部门的分配，不能删除正在被下级引用的岗位。

创建、改名、分配及调整层级使用现有组织写锁和修订号校验，防止并发绕过重名或引用校验。名称比较采用统一规范化。移动部门前按目标层级检查：若引入新的上下级重名，或使当前子树已有岗位引用失去祖先关系，返回具体部门与岗位，请管理员先显式处理；事务不提交部分修改。已有历史重名不会阻止与该冲突无关的编辑。

新增和撤销分配写入实际任职部门、岗位来源及岗位 ID 的审计信息；拒绝操作使用能定位来源或冲突部门的中文提示。接口失败后界面保留表单，冲突或修订号失效时提示刷新。

## 改动范围与风险

业务改动限定为：`backend/app/models.py`、`organization.py`、`roles.py`、`main.py`、`migrations.py`；三个现有组织和成员 Vue 组件。数据与文档涉及安装 schema、升级 SQL、`backend/scripts/organization_precheck.py`、部署说明及本变更记录；验证复用现有组织测试和浏览器脚本，并按需要新增岗位继承用例。

主要风险是把岗位来源误作成员归属、跨部门修改意外撤销角色、SQL 筛选与实际授权不一致、层级变化令已有引用失效，以及目录重复查询。所有分配变更统一走组织模块，前后端同时校验，目录延续批量汇总。

新增 `v1.0.6.sql`，保留 `v1.0.4.sql` 和 `v1.0.5.sql` 的升级历史；同步 `database/`、`docker-deploy/`、`k8s-deploy/` 及当前 SQL 分发目录和安装 schema。SQL 与启动迁移需支持重复执行及旧数据回填。远程 v1.0.3 依次执行 v1.0.4、v1.0.5、v1.0.6；本次涉及结构变化，不能只升级镜像。

## 验证与回退计划

- 接口和权限：多层祖先岗位可见、分配和撤销；一个人在多个部门引用同一岗位；原角色及项目保留；普通成员越权、部门负责人跨部门越权、不可委派模板拒绝；Python 授权与 SQL 角色筛选一致。
- 冲突与生命周期：创建、改名、并发重名；平级同名；历史重名保留；源岗位修改、停用、删除的引用影响；部门移动合法路径及失效引用/新增冲突拒绝，失败操作不改变原数据。
- 数据与性能：隔离 MySQL 重复执行升级、旧分配逐行核对、新装与迁移 schema 一致；目录查询数不随部门和岗位数量线性增加；子树人数及岗位人数去重。
- 界面：真实浏览器验证岗位来源、新建成员、添加已有成员、调整组织岗位和冲突提示，检查桌面与窄屏；执行相关后端回归、前端测试、构建和 schema 检查并记录实测结果。
- 部署前停止写入并备份数据库、密钥与镜像；迁移失败可在尚未恢复业务写入前恢复备份。开始使用继承分配后保留新结构与分配数据，不能直接降级到把定义部门当作任职部门的旧代码；优先关闭组织写入并修复或使用兼容新结构的回退版本，不删除新增关系。

## 决策记录

已批准：采用「岗位定义集中维护，任职部门独立记录」。这样同一个岗位能被多层部门复用，同一成员可在多个部门引用，且部门范围保持明确。未采用复制岗位到下级或自动合并同名岗位，避免产生多份模板及隐式角色变化。
