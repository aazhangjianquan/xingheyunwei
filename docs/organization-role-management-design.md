## 1. 需求简报

把「用户与权限」里的文本部门升级为管理员维护的组织目录。管理员创建部门、部门岗位和账号，明确指定部门负责人；成员的组织归属从目录中选择，负责人在本部门范围内管理人员岗位。

建议本次实现范围：部门层级、部门岗位、指定负责人、成员归属、部门与岗位下拉选择、权限校验、项目部门联动、历史数据迁移及审批兼容。继续使用现有平台角色目录作为权限模板。

本次不扩展到考勤、薪酬、飞书组织同步、多部门兼职或任意自定义权限表达式；保留一个用户属于一个部门、可以兼任多个部门岗位的模型。

### 验收标准

1. 管理员可以先创建空部门，在部门下建立「销售」「售前」等独立岗位，再添加成员、指定负责人；无人部门也能保留。
2. 添加成员、调整组织归属和创建／编辑项目时，只能选择已存在且启用的部门；伪造不存在的部门 ID、岗位 ID 或跨部门岗位也不能保存。
3. 普通成员不能创建组织项、修改自己的部门或岗位；现有业务中需要选择部门的位置只提供目录选项。
4. 部门负责人可以查看本部门人员并调整允许委派的岗位；跨部门、修改本人权限、管理管理员或其他负责人、授予系统权限等操作均被后端拒绝。
5. 销售和售前可以分别建岗、分配成员、分别统计；管理员可以把两个岗位都关联现有「销售/售前」业务权限。
6. 升级保留用户 ID、原有角色授权、项目成员、审批快照、已完成进度和审计记录；部门改名不会被当作成员调部门，负责人撤销后管理权限在后续请求立即失效。

## 3. 页面与操作流程

保留左侧「用户与权限」，进入后提供「成员管理」「部门管理」两个页签。平台角色继续在成员管理中由管理员维护。

```text
用户与权限
  ├─ 成员管理
  │    姓名／用户名 ｜ 所属部门 ｜ 部门岗位 ｜ 平台角色 ｜ 状态 ｜ 操作
  │    添加成员：账号信息 → 选择部门 → 选择该部门岗位 → 平台角色 → 保存
  └─ 部门管理
       左侧组织树                    右侧部门详情
       业务中心                      业务一部  [启用]
         业务一部                    负责人：张三、李四  [设置负责人]
         业务二部                    [成员] [岗位]
       研发部                        销售：王五、赵六
                                    售前：钱七
                                    [添加岗位] [添加成员]
```

此处姓名仅为设计示例。

### 管理员

1. 在部门管理点击「新建部门」，填写名称，可选上级部门、排序和说明。名称前后空白统一去除；首版部门名称全局唯一，历史名称也保留占用，避免旧审批文本产生歧义。
2. 部门创建后可为空，显示「待设置负责人」。管理员可以继续添加成员与岗位；需要负责人审批的申请，在没有合格负责人的情况下明确阻止提交。
3. 在部门的「岗位」页签创建「销售」「售前」等岗位，选择可选的权限模板，并设置是否允许部门负责人分配。
4. 通过部门详情添加成员：可以创建账号，或由管理员把已有账号调整到该部门。跨部门调整展示原部门、原岗位、负责人任命和待办影响。
5. 「设置负责人」从本部门启用成员中选择，支持一位或多位；多位负责人管理权限相同。取消负责人资格也在这里操作。
6. 新建／编辑用户和项目的所属部门均用组织选择器；用户岗位选项随部门联动，切换部门时清空原岗位草稿。

### 部门负责人

- 打开部门管理后只展示本人负责的部门；默认管理本部门直属成员，部门树层级不自动带来下级部门权限。
- 在「成员」页签查看成员、按岗位筛选，为本部门普通成员分配或撤销管理员允许委派的岗位；未分配岗位的人仍是该部门成员。
- 任命关系来自部门中的明确配置，不能仅凭给自己勾选「部门负责人」角色获得人员管理权限。
- 创建账号、人员跨部门调动、账号启停、重置密码、飞书绑定、平台角色直接授权、部门及岗位定义均由管理员操作。
- 本人、系统管理员、其他已任命的部门负责人以及持有四类职能负责人角色的成员，其岗位调整由管理员操作，避免通过岗位间接改变管理者权限。

### 普通成员

- 个人资料展示部门路径和岗位，组织归属由管理人员维护。
- 现有允许选择组织信息的业务表单使用目录下拉选项，不出现「输入即创建」或自定义选项。
- 当前没有普通成员自行选择所属部门的入口；本次也不新增自助调部门流程。

## 4. 组织岗位与平台角色的关系

组织岗位表示人员在部门里的职责；岗位关联的平台角色决定其具备哪些既有业务能力。任意岗位名均可创建，新增名称默认不增加平台权限。

| 部门 | 组织岗位 | 可关联的现有角色示例 | 部门负责人可否分配 |
| --- | --- | --- | --- |
| 业务一部 | 销售 | 销售/售前 `sales_presales` | 管理员允许后可以 |
| 业务一部 | 售前 | 销售/售前 `sales_presales` | 管理员允许后可以 |
| 研发部 | 产品开发 | 产品开发 `product_developer` | 管理员允许后可以 |
| 研发部 | 方案顾问 | 不关联权限模板 | 管理员允许后可以 |
| 运维部 | 运维人员 | 运维人员 `operator` | 首版由管理员分配 |

允许委派的角色模板白名单为：申请人、销售/售前、项目经理、智能体开发、产品开发、测试人员。岗位一旦包含白名单之外的角色，后端强制禁止负责人分配。管理员、License 管理者、知识库管理员、各类负责人、管理者及运维执行等权限继续由管理员直接维护。

岗位关联角色的新增、删除或调整仅管理员可做，保存前显示受影响成员、项目岗位和待办数量。负责人不能通过改岗位名称、权限模板或请求体绕过限制。

有效业务角色 = 管理员直接授权 ∪ 本人启用组织岗位关联的角色。角色展示标明「直接授权」「来自：业务一部 / 售前」等来源；同一角色有多个来源时合并生效，撤销某个岗位只移除该来源，不能误删直接授权或另一个岗位提供的权限。

新任命的部门负责人具备部门人员管理能力；其部门负责人审批身份也从任命关系派生。通用「部门负责人」不再提供独立手动授权入口，部门页为任命的唯一入口。四类职能负责人保留既有职责范围；他们只能维护职责内已有角色，或关联角色全部处于其职责范围内且允许委派的岗位，不能管理其他职能或未关联模板的自定义岗位。

组织岗位不自动加入项目，也不自动获得全平台业务、知识库、License Key 或凭据的查看权。项目岗位分配和对应业务资源的权限规则继续分别校验。

| 任命、撤销部门负责人 | 全部 | — | — | — |
| 创建账号、启停账号、重置密码、改飞书身份 | 全部 | — | — | — |
| 调整用户所属部门 | 全部 | — | — | — |
| 查看人员管理列表 | 全部 | 本部门 | 本部门 | — |
| 分配、撤销组织岗位 | 全部 | 本部门、允许委派的岗位 | 本部门且职责匹配、允许委派的岗位 | — |
| 直接调整平台角色 | 全部 | — | 保留现有职责内角色管理 | — |

所有写接口在事务内重新读取操作人、目标成员、部门、岗位及任命状态。前端隐藏操作和禁用按钮只用于表达权限，服务端为最终判断。角色兼任时权限按合法授权合并；「负责人不得改本人／管理者」限制适用于非管理员路径。

负责人失去任命、账号被停用或被调离原部门后，下一次请求立即失去原管理范围；不依赖重新登录或浏览器保存的角色标签。

## 6. 数据与接口方案

### 数据实体

| 实体 | 核心字段与约束 |
| --- | --- |
| `departments` | `id`、`name`、`parent_id`、`active`、`sort_order`、`description`、`revision`、`approval_mode`；父子关系禁止循环，首版当前名及历史别名全局不可重名 |
| `department_aliases` | 历史名称 → 部门 ID；服务于旧流程条件和旧任务快照兼容，不作为可选组织项 |
| `department_managers` | `department_id`、`user_id`；组合唯一，必须是本部门启用成员；任命显式维护 |
| `department_positions` | `id`、`department_id`、`name`、`active`、`manager_assignable`、`revision`；同部门岗位名唯一 |
| `department_position_roles` | `position_id`、现有 `role` ID；组合唯一，角色 ID 经现有别名规范化后校验 |
| `department_user_positions` | `user_id`、`position_id`；组合唯一，岗位必须属于用户当前部门 |
| `users`、`projects` 增量字段 | 新增 `department_id` 外键；旧 `department` 作为过渡显示字段，由组织服务同步，不再接受任意文本写入 |

新成员和新项目必须选择部门。历史空部门暂保留空值并标记「待分配」；仅涉及其他资料的保存不强迫补全，下一次修改组织归属时须选择有效部门。

启用状态、权限来源和负责人资格统一从组织服务计算，角色工具函数和 SQL 范围查询使用相同的有效授权定义；避免页面显示有权限、列表查询却漏掉岗位授权的情况。继续使用 Vue、FastAPI、SQLAlchemy 和 MySQL，不引入新的运行依赖。

### 接口草案

| 接口 | 作用与权限 |
| --- | --- |
| `GET /api/organization/options` | 登录用户读取业务所需的启用部门 ID、名称、层级和岗位选项；不返回账号标识、飞书身份或人员管理信息 |
| `GET /api/departments` | 管理员读取全部组织管理信息；部门及职能负责人仅读取自己的管理范围 |
| `POST /api/departments`、`PATCH /api/departments/{id}` | 管理员创建、改名、调整层级或启停；提交 `revision` 防止旧表单覆盖新配置 |
| `PUT /api/departments/{id}/managers` | 管理员设置完整负责人集合，进行部门、账号、任命及待办影响校验 |
| `GET/POST /api/departments/{id}/positions`、`PATCH /api/department-positions/{id}` | 按范围读取岗位；定义与权限模板写入仅管理员可用 |
| `PUT /api/users/{id}/organization` | 管理员原子保存部门和岗位；部门／职能负责人只能提交范围内岗位调整，后端保留其无权调整的岗位 |
| 现有用户、项目写接口 | 改为接收 `department_id`；用户创建另接收 `position_ids`；文本 `department` 写入明确拒绝，响应继续提供部门显示名 |
| `GET /api/me`、用户列表响应 | 增加部门 ID、部门路径、岗位、角色来源、人员管理能力；前端依据服务端能力显示入口 |

人员管理接口与项目／流程中的轻量人员选择器分别按用途过滤和裁剪字段，不能因负责人只能看本部门管理列表而破坏已有跨部门项目协作。

无权限返回 403，不存在的组织项返回 404，已停用、跨部门、不满足状态约束或版本冲突返回 409，请求字段非法返回 422；错误提示说明具体部门／岗位和可执行的处理方式。

## 7. 状态、边界与审批联动

- **部门层级：** 禁止自己作为上级、把部门挂到自己的后代、把启用部门挂到停用部门；层级只表达组织结构，负责人权限按明确任命计算。
- **改名：** 部门 ID 不变，旧名称保存为别名，用户与项目的过渡显示字段同步更新；不能把旧名称分配给另一个部门。新权限判断使用 ID。
- **调部门：** 管理员提交前查看影响；事务中移除原部门岗位和原负责人任命，写入新部门与新岗位。保留直接角色和独立项目成员关系，失去对应有效角色的项目岗位标记「需调整」，不自动替换项目负责人或删除历史关系。
- **岗位停用或权限模板调整：** 先预览有效角色、项目资格和待办影响；已有岗位关系保留作追溯，停用岗位不再提供有效角色，也不能新增分配。仅撤去某个来源的角色，其他来源继续有效。
- **部门停用：** 有启用成员、启用项目、启用子部门或未完成的部门审批任务时阻止停用，返回阻塞项与数量。使用停用保留关联和历史，本次不提供物理删除。
- **负责人调离／停用／撤销：** 展示待办影响；允许管理员调整，管理能力立即撤销，待办通过已有管理员转交功能恢复；不会把审批自动交给新负责人。
- **新部门审批：** 「部门负责人」节点匹配明确任命且启用的负责人，排除申请人。未配置、全部不合格、人数不足或唯一负责人就是申请人时，阻止提交并提示配置；不能自动借用其他部门负责人。
- **现有部门审批兼容：** 自动导入的部门先使用 `legacy_roles` 模式，保留原显式部门负责人及职能负责人兜底规则；管理员确认负责人集合时切换为 `designated_managers`。新建部门默认后一模式。确认前展示审批处理人变化及会签人数影响，不自动扩大任命权限。
- **身份兼容：** 旧的通用 `department_head` 授权在兼容模式下继续支持原审批规则，但不据此增加人员管理权；确认任命后，当前部门负责人身份以任命关系为准，旧授权保留记录且不再绕过任命生效。四类职能负责人身份继续由其直接授权维护。
- **在途审批：** 不改原快照、处理人和已通过节点；资格检查仍读取实时账号、角色及归属，失去资格的原处理人不能继续处理，由管理员显式转交。历史部门负责人兜底规则仅用于旧快照所需的资格兼容，不能授予人员管理能力或新任命后的负责人身份。
- **快照与条件：** 新审批保存部门 ID、提交时名称及部门来源；旧快照通过唯一历史别名定位部门。未能唯一定位时拒绝处理并提示管理员修复。旧流程版本的文本部门条件由兼容层解析，新流程选择部门 ID；已存版本和审批意见不做文本替换。
- **申请归属：** 普通成员继续按申请人所属部门匹配，管理员继续按所选项目所属部门匹配；排除自审、会签／或签／N 人同意及项目参与资格继续校验。
- **并发与失败：** 组织写操作校验修订号；组织、人员和授权更新使用一致锁顺序并在事务内重新检查。授权变更与审计同事务，任何一项失败则整体回滚。冲突提示刷新重试，保存失败保留表单内容。

## 8. 历史迁移与部署

1. 先备份现有数据库和部署版本。只读预检查统计用户、项目中的部门名称、空值和规范化后的重名冲突；数据库排序规则引起的其他冲突由初始化迁移再次拦截。旧流程文本部门条件由别名兼容层读取，不改写历史版本。
2. 增量创建组织表和可空外键；将非空的用户、项目部门去重导入。只有项目、尚无成员的部门也保留；不从历史审批文本凭空创建活动部门。
3. 精确名称建立引用。前后空白等差异列入报告，保存可唯一定位的旧名称别名；可能合并不同实际部门的冲突停止该映射并交由管理员确认，不能静默合并。
4. 旧岗位没有独立关系，不凭角色猜测「销售」还是「售前」。原直接授权完整保留，成员初始可显示「未分配组织岗位」，由管理员补齐。
5. 对原显式部门负责人和四类职能负责人展示候选与「待确认负责人」。不把候选人自动任命为新的人员管理者。保留原审批匹配模式，逐部门确认后切换。
6. 初始化路径覆盖现有库、首次管理员、演示种子及重启；先建组织再写引用，升级可重复执行，已确认任命和已撤销授权不能在重启时被重建。
7. 先部署能读取新旧字段和历史别名的兼容版本，再启用目录写入。多 API 副本与 Worker 必须升级到一致版本；数据库升级继续使用现有全局初始化锁，写入切换期间暂停 API／Worker。
8. 输出迁移数量、未分配人员、命名冲突、待确认负责人、流程兼容与异常项；检查通过后启用组织管理。角色授权或组织归属不能在迁移中静默清空。

升级 SQL 使用版本化的 `v1.0.4.sql`，在 `database/`、`docker-deploy/`、`k8s-deploy/` 和 `sqlscirpts/` 同步维护；同时更新当前安装结构，避免首次安装与升级后的结构不一致。

## 10. 验证计划与回滚

已在独立 SQLite 和 MySQL 8.4 测试库完成回归、页面与迁移验证；未访问或修改现有平台的真实成员数据。实际执行命令、结果及未覆盖范围见实施与验收记录。

实现时复用现有 `backend/tests/test_roles_departments.py`，并运行相关用户／分页、项目／流程迁移、License、个人资料与审计用例，以及相关前端用例和构建。新增验证聚焦下列实际边界：

- 空部门保存、层级循环、重名、跨部门岗位、停用组织项以及直接构造 API 请求。
- 普通成员、部门负责人、职能负责人和管理员四种身份；本人／其他管理者保护、委派模板绕过和撤权即时生效。
- 多岗位提供同角色、直接授权叠加、撤销单一来源、岗位停用及跨部门调动。
- 管理列表与轻量选择器各自范围，原跨部门项目协作、至少一位项目经理、原有凭据与 Key 可见范围。
- 新旧部门审批模式、改名后的在途任务、文本条件、本人不能自审、会签人数不足、失效待办转交。
- 旧库升级两次、空白／重名冲突、原负责人候选确认、多副本初始化及首次管理员。
- 真实页面上的页签、树与成员联动、加载失败重试、保存失败保留内容、移动端布局及停用／确认影响提示。

回滚不能只恢复旧应用镜像：旧版本不认识组织岗位提供的角色，也无法正确处理部门改名后的别名。

1. 写入切换前可回退应用；新增表和可空字段保留，不执行删表回滚。
2. 写入切换后先暂停组织修改并备份新数据，回退到支持部门 ID、历史别名、授权来源和任命规则的兼容版本。兼容版本是本次交付的一部分，需要验证后保留。
3. 如必须恢复完全不支持组织功能的历史版本，先制定角色物化与部门／旧快照映射方案，再停写执行并验收。整库恢复升级前备份会丢失升级后的业务写入，须另外处理，不能作为自动回滚。

## 11. 设计决策记录（已批准并实现）

- 采用独立组织目录和稳定 ID，因为空部门、任命、改名及启停都需要独立实体。
- 采用自由命名的部门岗位并关联现有角色模板，因为用户需要分别管理销售和售前，同时现有项目与审批仍依赖角色 ID。
- 采用明确任命的负责人关系作为人员管理依据，因为当前通用部门负责人角色只有审批能力，不能继续依赖名称和职能角色猜测任命。
- 采用按来源合并的有效授权，避免把岗位权限直接覆盖到原 `user_roles` 后无法安全撤销。
- 采用历史部门逐个确认负责人及审批切换，避免升级自动增加人员管理者或改动在途流程。
- 用户以「可以的」批准本方案后实施；新增组织服务集中处理迁移、权限与授权来源。首次管理员沿用原初始化入口，在同一初始化流程中回填部门，无需修改 `bootstrap.py`。审计使用已有动态类型选项，无需修改 `AuditLog.vue`。
- 并发写入先结束鉴权只读事务，再按部门、人员顺序加锁并重新读取授权，避免 MySQL 默认隔离级别保留加锁前的旧快照；岗位编辑也重新读取修订号。
