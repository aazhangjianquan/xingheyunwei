# 多部门成员与汇总人数调整

> 本文保留前次实施记录。用户已要求移除额外部门标记和审批设置，当前行为以 [部门成员界面简化](organization-simple-membership-change.md) 为准。

2026-11-06。依据用户最新明确指令实施，取代此前已确认的单一部门调入规则。

## 范围、现状与设计

当前组织目录的 `member_count` 只读取 `users.department_id`，顶级部门不汇总子部门。调部门时 `assign_organization` 清空原岗位并撤销全部负责人任命；有效角色和审批资格也只认主部门。UI 选项因此不能表达多部门。

新增独立成员部门关系，保留原 `users.department_id` 为主部门兼容字段，用于新申请默认审批归属。主部门切换和加入其他部门都不移除原部门关系、岗位或任命；岗位只在管理员明确编辑该部门时调整，直接角色继续仅由管理员维护。原项目关系、历史快照和直接角色不修改。已有主部门回填为成员部门，重复升级不增加重复记录。

部门树显示本部门及全部后代成员的去重人数；部门详情分别显示直属人数与含下级总人数，默认列表为直属成员，并提供含下级查看选项。一个人出现在多个子部门时在上级总数只计算一次。部门负责人只管理明确任命的部门，不因加入其他部门而获得管理权。负责人任命和审批匹配均支持兼职部门，且按快照对应的具体部门核验。

涉及组织模型、集中权限规则、成员筛选、流程匹配、组织界面及部署 SQL。保留既有委派范围限制；新增、移除部门关系以及主部门切换由管理员操作。移出某部门需显式操作，删除该部门对应的岗位及任命；主部门须先切换后才允许移除。

## 验收与风险

覆盖多层部门汇总与重复人员去重、多部门成员列表、主部门切换保留角色/岗位/任命、管理员显式移除、负责人跨部门边界、具体部门审批资格、迁移幂等和查询数增长。隔离库验证所有写操作；线上验收只读。

新增关系表为加法迁移。部署前暂停写入备份数据库、实例密钥与镜像，对原业务表、岗位、负责人和审批版本逐行摘要核对；只允许新增成员部门关系回填，不改原行。回退须保留理解多部门的兼容读取，不删除关系表、不直接恢复整库覆盖后续写入。


## 实施与验证记录

新增 `department_memberships` 关系及七张组织表的安装/升级 SQL 支持；成员输出同时提供所有部门、主部门、各部门岗位与明确管理范围。管理员可以从全平台添加已有成员、选择是否设为主部门，或显式移出某个非主部门。只更新当前提交部门的岗位，原部门、原岗位及任命不隐式删除。

部门树按整个子树的用户集合计数；详情同时显示直属与含下级总数，管理员可切换查看直属/含下级成员，列表按成员 ID 去重。审批保留主部门默认归属，并按实际审批部门检查兼职负责人任命；主部门变化不会撤销原审批资格，撤销具体部门任命才使该部门资格失效。历史实例、已发布版本及原项目关系保持不变。

后端相关 107 项检查无失败（2 项真实 Java 条件跳过），覆盖新增多部门、去重、保留岗位/任命、显式移除和具体部门权限。前端 133 项检查通过，生产构建成功。浏览器在隔离 SQLite 中通过 17 项检查，验证加入两部门、切换主部门、原岗位和任命保留、上级去重与列表一致，以及桌面和 390px 布局。查询数为 `/api/me` 8 条、`/api/projects` 16 条；项目从 22 增至 42，查询数不增长。证据：`reports/organization-multi-backend-tests.log`、`organization-multi-frontend-tests.log`、`organization-multi-ui-tests.log`、`organization-multi-build.log`。

## 决策与回退

采用“一个主部门＋多个同时加入的部门”以保持现有申请归属和审批默认规则明确；加入其他部门不改变主部门，管理员需要时可另行勾选主部门。成员权限取仍有效来源的并集，负责人管理范围按具体部门任命判断，加入另一个部门本身不扩张管理权限。组织树统计直属和后代成员集合的并集，不把各子部门人数直接相加。

新增部门关系表不执行删除回滚；发布前后保护所有原业务行、组织岗位与任命、流程版本及主密钥，只允许补入原主部门关系。需要暂停维护时使用组织只读开关；不自动把多部门数据降级回单一部门模型。
