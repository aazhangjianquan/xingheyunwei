# v1.0.1 角色与部门职责

## 角色分组

| 分组 | 角色 |
| --- | --- |
| 基础与系统 | 申请人、管理员、License 管理者、知识库管理员（保持原有权限） |
| 审批与执行 | 部门负责人、运维负责人、管理者、运维人员、测试人员、商业化负责人、项目经理负责人、技术负责人、智能体开发负责人 |
| 项目与业务 | 销售/售前、项目经理、智能体开发、产品开发 |

角色支持多选。新增角色不会自动插入已经发布的审批流程，需要时由管理员在流程中选择岗位并发布。

## 负责人管理范围

| 负责人 | 可授予、撤销的成员岗位 | 范围 |
| --- | --- | --- |
| 商业化负责人 | 销售/售前 | 本部门 |
| 项目经理负责人 | 项目经理 | 本部门 |
| 技术负责人 | 产品开发 | 本部门 |
| 智能体开发负责人 | 智能体开发 | 本部门 |

负责人进入「用户与权限」后，只显示本部门成员，可以调整对应岗位。不能给自己加权限，不能调整他人管理员、负责人等职责以外角色，也不能停用账号、重置密码、修改飞书身份或改部门。承担多个负责人职责时，管理范围合并，仍限制在本部门。

管理员在「添加成员」或「管理角色」中填写、修改所属部门。可选择已有部门，也可以直接填写新部门。部门继续沿用原有 `users.department` 字段，名称一致即视为同一部门，不需要新增部门表或环境变量。授予四类负责人角色时必须有部门；同一部门可有多位负责人。

「用户与权限」支持部门筛选，并展示所选部门的负责人。负责人离职、停用、变更部门或角色撤销后，下一次请求就重新校验，无需重新登录。

## 审批和项目联动

- 流程节点选择「申请归属部门岗位 → 部门负责人」时，优先使用显式授予“部门负责人”的成员；没有合格的显式负责人时，自动匹配本部门上述四类业务负责人。申请人本人及停用成员会排除。保留会签、或签、任意 N 人同意配置。
- 如果只需要某个职能负责人审批，可直接选择「申请归属部门岗位 → 商业化负责人 / 项目经理负责人 / 技术负责人 / 智能体开发负责人」，不依赖额外授予“部门负责人”角色。
- 普通申请按申请人部门匹配；系统管理员申请按关联项目部门匹配。既有审批快照、审批意见和待办分配保持原样；处理任务时重新校验角色和部门。
- 项目至少保留一位项目经理。项目经理可维护参与项目的其他岗位；项目经理任免由管理员或本部门项目经理负责人维护。
- 四类业务负责人可查看本部门项目岗位并维护各自负责的岗位。此管理能力不赋予项目申请资格或读取全部业务单据的权限；申请仍需实际项目岗位授权。
- 测试人员作为可选审批或项目岗位使用；运维执行/回填节点继续要求运维人员。
- 管理者沿用原“领导”的业务权限。知识库和 License Key 的既有可见性规则保持原样。

## 旧角色兼容和 SQL

| 旧角色 | 新角色 |
| --- | --- |
| 领导 | 管理者 |
| 项目负责人 | 项目经理 |
| 项目总监 | 项目经理负责人 |
| 销售/售前负责人、销售/售前总监 | 商业化负责人 |
| 开发负责人 | 技术负责人 |

上述映射同时用于用户角色和项目岗位，合并重复授权。旧角色 ID 仍由新版后端识别，避免历史流程或固定审批任务因角色改名失效。历史审批记录、版本、日志不做文本替换。

升级文件是 `v1.0.1.sql`，在 `database/`、`docker-deploy/`、`k8s-deploy/` 各保留一份，内容相同。这是已有数据库的角色数据迁移，可以重复执行，不含测试数据；不会重置密码、清空业务或重建已撤销的角色。不重新执行 `v1.0.0.sql`。

正式部署：备份已有库，停止 API 和 Worker；连接原业务库执行 `v1.0.1.sql`；更新 API、Worker 和前端镜像并启动。升级后检查原有角色映射以及每位负责人的所属部门。无需添加环境变量或目录挂载。
