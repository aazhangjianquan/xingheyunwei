日期：2026-11-06（北京时间）。用户以「可以的」批准 [设计方案](organization-role-management-design.md) 后实施。采用本地 `req-change-workflow` 开发 skill。最新规则以 [部门成员界面简化](organization-simple-membership-change.md) 为准。开发阶段使用独立测试数据；用户随后明确要求「部署升级」，已更新本机平台，部署记录见文末。

## 使用方法

1. 管理员进入「用户与权限 → 部门管理」，新建部门，可设置上级、排序、说明和启用状态；部门可以暂时没有人员。
2. 选中部门，在「岗位」中分别创建「销售」「售前」等岗位。名称自由填写，权限模板选用已有平台角色。允许负责人分配的岗位还须满足后端委派白名单；系统管理员、License 管理者、知识库管理员和通用部门负责人不能通过岗位模板授予。
3. 在部门成员页使用「新建成员」添加账号，或通过「添加已有成员」从全平台选择并加入；原部门关系、岗位、负责人任命、直接角色和项目关系保留。每人可加入多个部门，在各部门保留岗位和负责人任命；成员界面只展示所属部门和岗位。创建成员和创建／编辑项目的部门只能从启用目录中选择；接口也拒绝任意文本部门。
4. 点击「设置负责人」，从本部门启用成员中选择一人或多人。负责人获得本部门普通成员的可委派岗位管理能力；层级不自动授予下级部门管理权。
5. 普通成员在个人资料查看部门路径和岗位。负责人不能修改本人、其他管理者或跨部门人员，不能创建账号、重置密码或直接授予系统权限。这些操作由管理员完成。

平台角色显示授权来源：直接授权、部门岗位或负责人任命。撤销一个岗位仅移除该来源，其他岗位和原直接授权继续生效。项目岗位独立维护；组织调整使其失去资格时，项目中显示需调整，不自动删除项目关系。

## 旧数据与审批

- 用户与项目中非空的历史部门名称导入组织目录，包含只有项目、没有人员的部门。原空值保留「待分配」。名称规范化发生冲突时停止迁移，不静默合并。
- 原用户 ID、密码哈希、直接角色、项目成员及审批快照和意见保留。不从原角色猜测销售／售前岗位，也不自动任命负责人。
- 历史部门提示补齐负责人；所有新申请均只匹配明确任命。第一节点默认选择紧邻上一级部门负责人，顶级部门使用本部门负责人；缺少任命、负责人停用或仅有申请人本人时阻止提交并提示。审批流程可显式设置本部门或上一级部门。
- 新部门直接使用明确任命。申请人不能自审；负责人不足以满足会签阈值时阻止提交。部门改名保留 ID 和历史别名，旧流程文本条件与任务快照继续识别。
- 已有待办不自动换人。撤销任命、停用或调离使原处理人失去资格后，管理员通过原转交功能恢复处理。

## 升级顺序

先备份原数据库和主密钥，并保留当前镜像版本。准备新版 API、Worker、提醒调度服务和前端镜像；所有副本需使用一致的权限规则。

新版 API 镜像包含只读预检查脚本。Compose 可在对应部署目录运行：

```sh
docker compose run --rm --no-deps api python scripts/organization_precheck.py
```

从源码运行时，使用既有数据库配置和主密钥环境：

```sh
python backend/scripts/organization_precheck.py --output reports/organization-precheck.json
```

脚本不启动 API、不执行迁移、不修改业务数据。输出部门数量、空归属数量、规范化名称冲突、待确认部门和未分配岗位人数；名称冲突返回退出码 2，需要确认并处理原名称。此工具不逐条扫描历史流程版本；旧文本条件的兼容由服务读取和回归测试验证。

暂停 API、Worker、提醒调度服务写入，通过原业务数据库连接执行 `database/v1.0.4.sql`（Docker、K8s、`sqlscirpts/` 目录提供完全相同副本），再启动新版服务。脚本可重复执行，只补表、字段、索引和外键；实际部门名称回填由 API 初始化完成。直接启动新版 API 也支持自动升级；多副本初始化沿用现有 MySQL 全局命名锁。

升级后刷新浏览器，管理员检查成员和项目归属，逐部门补齐岗位并确认负责人。仅导入 SQL、仅重启旧镜像或只更新前端，都不能完成组织管理升级。全新安装的结构 SQL 已同步包含七张组织关系表。

## 实现与决策

| 决策 | 原因与实现 |
| --- | --- |
| 使用独立组织目录与稳定 ID | 支持空部门、层级、启停、明确任命；名称变化不改变归属。核心规则集中在 `backend/app/organization.py` |
| 岗位与直接角色分别保存 | 有效角色按来源合并，避免撤销岗位误删原有授权；保留现有业务角色目录 |
| 负责人显式任命、新申请统一组织来源 | 避免旧职能角色继续管理人员；历史任务仍按冻结快照识别原身份 |
| 服务端范围校验与修订号 | 拒绝跨部门、自改权限和陈旧表单；前端根据服务端能力展示操作 |
| 加锁后重新读取授权 | 写事务入口先结束鉴权阶段只读事务，再按固定顺序锁部门与人员，避免 MySQL REPEATABLE READ 读取加锁前的旧授权快照；岗位更新重新读取修订号 |
| 保留当前兼容读取，提供维护开关 | `ORGANIZATION_WRITES_ENABLED=false` 阻止组织配置和人员归属写入，保留目录读取和直接角色维护；不是旧镜像降级开关 |

未采用把岗位角色直接写回原 `user_roles` 的方式，因为无法区分授权来源；也未采用从职能负责人自动推断组织负责人，避免扩大管理权限。

MySQL 新装验证发现原有 TEXT 默认值使用了 MySQL 不支持的字面量形式。已将安装 SQL 和旧表增量定义中的空文本默认值改为表达式，并把资源规格 JSON 的 ORM 默认值改为 MySQL 兼容表达式；业务默认内容保持一致。

## 维护与回退

如需暂停组织调整，在所有 API 副本设置 `ORGANIZATION_WRITES_ENABLED=false` 并重建容器／Pod。继续保留本次兼容版本读取部门 ID、历史别名、岗位角色及任命关系；组织写接口返回只读维护提示。该开关不暂停其他业务单据或项目编辑。

新增表和字段不执行删除回滚。已启用岗位授权或发生部门改名后，不应直接运行不理解这些数据的旧镜像。若必须恢复旧版，需停写并单独处理角色来源物化及旧部门映射；整库恢复升级前备份会丢失升级后的写入，不能自动执行。
